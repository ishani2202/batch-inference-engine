## 1. What this project is

This is a take-home technical assessment for DigitalOcean's Agentic AI role (IC4/IC5 level). The task is called "Batch Inference Engine REST API Service." We have 2 days but are aiming to finish in 1.

In plain words: a small backend service that takes a file of 1,000 LLM prompts, sends them to an AI model in parallel, handles rate limits and failures without losing anything, and returns all the results. Reviewers are mid-to-senior engineers. They care about correctness, clear reasoning, sensible tradeoffs, and proof that the system works under pressure. Clean, readable, well-explained code matters more than clever code.

## 2. Requirements from the assessment document

Functional:
- Read and parse a local input file, `sample_batch.json`, containing an array of 1,000 prompt items. Return a job ID instantly. Execution runs in the background, fully unblocked.
- Split the prompts into chunks and run them across a bounded internal worker pool that calls live inference endpoints. Prefer a cost-efficient model (the document suggests `meta-llama-3-8b-instruct`).
- Handle HTTP 429 rate limits with exponential backoff and jitter. Maximize completion speed without dropping any items.
- Isolate individual failures (persistent 500s, corrupt inputs) as errors without stopping the job.
- `GET /job/{id}/status` to track progress. `GET /job/{id}/download` to get the final compiled array of results.

Engineering:
- An architecture diagram showing: input ingestion, the scatter (worker) pipeline, the backpressure/throttling layer, and the gather (results) layer.
- An explanation of scaling limits: if input grows to 500,000 items, how the code avoids out-of-memory crashes.
- Unit and integration tests covering all scenarios.
- A GitHub Actions pipeline that runs the full test suite on every push.
- A README with quickstart commands for the 1,000-prompt input and an explicit discussion of scale thresholds.

Extensions (building both):
- Persist intermediate results progressively to a DigitalOcean Spaces bucket, so large jobs survive crashes.
- Support a completion webhook: the caller registers a URL, and we notify it when the job finishes.

`sample_batch.json` is generated by `scripts/generate_batch.py` unless the recruiter provides one.

## 3. Architecture

```
                    POST /job  (optional: webhook_url)
                         |  returns job ID instantly
                         v
+---------------------------------------------------------+
|  Job Manager  (tracks status, counts, metrics per job)  |
+---------------------------------------------------------+
                         |
   sample_batch.json --> Streaming Reader  (reads items one at a time)
                         |
                         v
                   Bounded Queue  (max ~100 waiting)
                         |
          +--------------+--------------+
          v              v              v
       Worker         Worker   ...   Worker     (fixed pool)
          |              |              |
          +------> Shared Speed Controller <---- 429s slow everyone down,
                         |                        smooth runs speed back up,
                         v                        respects Retry-After
              DigitalOcean Inference API
              (URL, key, model all from env vars)
                         |
         success --------+-------- failure after retries / bad input
                         v
               Results Writer  (one line per result, straight to disk)
                         |
          +--------------+------------------+
          v              v                  v
   results.jsonl   errors.jsonl    DigitalOcean Spaces
                                   (chunks uploaded as you go)
                         |
                         v
             Job done --> Webhook call to the given URL

   GET /job/{id}/status    -> progress, failures, retries, speed, cost
   GET /job/{id}/download  -> streams results from disk
```

## 4. Components

- **API layer (`app/main.py`)**: FastAPI, `POST /job`, `GET /job/{id}/status`, `GET /job/{id}/download`. POST validates, creates the job, starts a background asyncio task, returns the ID immediately.
- **Config (`app/config.py`)**: all settings from env vars via `pydantic-settings`.
- **Streaming reader (`app/reader.py`)**: `ijson`, yields `(index, item)`, never loads the whole file.
- **Bounded queue + worker pool (`app/workers.py`)**: `asyncio.Queue(maxsize=QUEUE_SIZE)`, fixed number of workers. Reader waits when the queue is full (real backpressure).
- **Shared speed controller (`app/rate_limiter.py`)**: AIMD concurrency limit shared by all workers; 429 halves it, successes grow it, `Retry-After` pauses new calls.
- **Inference client (`app/inference.py`)**: `httpx.AsyncClient`, OpenAI-compatible chat completions. Retries 429/5xx/timeouts/connection errors with full-jitter exponential backoff (base 1s, cap 30s), respects `Retry-After`, never retries other 4xx, stops the whole job on 401/403. Reads `usage` for tokens.
- **Input validation**: item must be an object with a non-empty string `prompt`; otherwise it goes to errors without an API call.
- **Storage (`app/storage.py`)**: `output/{job_id}/meta.json`, `results.jsonl`, `errors.jsonl`, appended line by line. Every record has `index` and `id` (if present).
- **Crash recovery**: on restart, resume running jobs by skipping indexes already in the JSONL files.
- **Download**: streams a JSON array built from `results.jsonl`, completion order, each record has `index`. 409 while running.
- **Job manager (`app/jobs.py`)**: status + metrics (total, done, succeeded, failed, retries, 429s, current concurrency, times, items/sec, tokens, estimated cost).
- **Spaces upload (extension)**: upload result parts to a Spaces bucket as the job runs (boto3, S3-compatible). Skipped if not configured.
- **Webhook (extension)**: optional `webhook_url`; POST a summary on finish, retry with backoff; failures never change the job result.
- **Input path safety**: input file must resolve inside `DATA_DIR`.

## 5. Model and provider

DigitalOcean Serverless Inference: `https://inference.do-ai.run/v1/chat/completions`, Bearer model access key, OpenAI-compatible. Check `GET /v1/models` before choosing. Use the spec's Llama 3 8B if available; otherwise the cheapest small text model, explained in the README. Keep `MAX_TOKENS` low (~128).

## 6. Testing strategy

1. Mocked tests (`respx`) are the main suite: no real API calls, no key, runs in CI.
2. A few real calls while developing to check key/URL/model.
3. One real 1,000-prompt run at the end; results go in the README.

Why mocks: a 429 or 500 is a status code from the server, not something a prompt can trigger, and the real API won't produce it on demand. Retry delays are configurable so tests run in milliseconds.

## 12. Decisions log (after the original handoff)

1. **Slots are released during backoff.** A worker holds a controller slot only while its HTTP request is in flight. It sleeps between retries without a slot, so a backing-off worker never blocks others.
2. **One 429 burst = one cut.** Each slot is stamped with the controller's current "epoch". A 429 only halves the limit if the request started after the last cut. Otherwise 30 simultaneous 429s from one burst would halve the limit 30 times (to the floor).
3. **Slow start, then additive increase (like TCP).** Until the first 429, the limit grows +1 per success (doubles per round). After a 429, it grows +1 per `limit` successes in a row (roughly +1 per round). This replaces the fixed "+1 per 20 successes", which would take ~500 requests to climb from 8 to 32 on a 1,000-item job.
4. **Pre-flight validation pass.** Before calling any API, the job streams the whole file once (flat memory) to count items and verify it is valid JSON. A malformed file fails the job before a single paid call; it also gives the status endpoint a real `total`.
5. **Local prompt size guard.** `MAX_PROMPT_CHARS` (default 32,000) rejects oversized prompts before spending money. The API's own 4xx for context overflow is still handled as a non-retryable error.
6. **Download returns successes; errors are separate.** `GET /job/{id}/download` returns the successful results array (what the spec asks for). `?kind=errors` returns the errors array.
7. **Crash recovery details.** `meta.json` stores the input path and webhook. On startup, jobs left `running` are resumed. A half-written last JSONL line is truncated before appending. Delivery is at-least-once per item.
8. **boto3 runs in a thread** (`asyncio.to_thread`) so Spaces uploads never block the event loop.
9. **Assessment PDF is not committed** (`docs/*.pdf` is gitignored).
10. **Webhook SSRF** is noted in "What I'd do next"; no code change.
11. **Model: `mistral-3-14B`.** Llama 3 8B is not offered on DO (`GET /v1/models`). Ministral 3 14B is small, open-weight, non-reasoning, $0.20/$0.20 per 1M tokens. Cheaper reasoning models (gpt-oss-20b, gpt-5-nano) risk empty answers under a 128-token cap.
12. **402 Payment Required is fatal** (`BillingError`), like 401/403: it is account-wide, so every item would fail the same way.
13. **Real DO limit is a rate, not concurrency.** Headers show `x-ratelimit-limit-requests: 120` (~2 req/s), no `Retry-After` on 429s. The concurrency controller finds the ceiling but can't prevent every 429. Header-aware pacing is a possible next step (undecided).
14. **404 is fatal** (`ConfigError`): DO returns `404 "model not found"` for an unknown MODEL (verified with a real call); on the chat endpoint a 404 is always job-wide (model or URL).
